# План рефакторинга adev — маршруты, документы, вопросы, фронтенд

Статус: черновик, согласован с реальным кодом на `adev/` (коммиты до `14582a2` включительно).
Источник правды по маршрутам — `docs/Arhitecture.md` и `form-registry/`.

## Цель

1. Привести pipeline к модели «двигается только по валидным документам» (убрать draft-при-движении и дубли HLD/BRD).
2. Реализовать стадию 01 по плану: TEJ xor RAR (решает оператор) + BRD-clean, в SRS попадает только BRD-clean.
3. Разделить SRS на два документа FR и NFR и ввести fan-out по каждому требованию.
4. Вернуть вопросы на архитектурные стадии (принцип «не уверен → operatorQuestion + варианты»), вопрос с выбором и без падения от ответа.
5. Убрать голый JSON, сделать вкладки Dashboard / Settings / Docs / Questions.
6. Подготовить код к маршруту Change (Route A/B) и стадиям 07–09 + цикл 08.R→09.
7. Закрыть накопившиеся нарушения OCP/SRP: промпты как данные, спецификация формы в таблице, учёт вызовов модели, контекст по formID.

## Порядок и зависимости

```
PR0 (швы) ──► PR1 (identity/статус) ──► PR2 (вопросы) ──► PR3 (01) ──► PR4 (SRS fan-out) ──► PR5 (фронт) ──► PR6 (change+07–09)
                                                                                              └─► PR7 (2.1–2.9)
```

PR0 обязателен первым: он делает дешёвыми новые типы форм (PR3, PR4, PR6) и убирает литералы промптов. PR1 и PR2 можно менять местами, но PR2 без PR1 оставит статусы лживыми.

## Вне плана (осознанно отложено)

- **Суб-пайплайны как движок**: пока не нужны; батчи PR4 покрывают «большой ответ». Вернуться, когда появятся параллельные ветки по FR/NFR.
- **Контекст-бюджет / суммаризация / эмбеддинги**: пока хватает «только последняя принятая версия + ключ по formID».
- **Шлюз/роутер моделей (квоты, маршрутизация)**: порт `LLMFactory` — правильный шов; добавить позже без правки стадий.
- **Утверждение оператором (`approved`) как отдельный шаг**: не входит в запрос; `valid` = гейты прошли и вопросов нет. Если нужен человеческий гейт на каждую стадию — отдельный PR после PR2 (эндпоинт статуса уже есть).

## Риски

1. **PR0 меняет сигнатуру `LLMRequest` и раскладку контекста** — затронет адаптер, моки и тесты стадий; поведение должно остаться тем же, проверять полным прогоном 00→06.
2. **PR1 меняет выбор документов по стадиям** — старые пайплайны с двойниками (`FRM-1-01-BRD`, `FRM-1-04-HLD`) остаются в таблице как история; после PR1 перегнать стадии 03+ на пайплайне 1.
3. **PR2/PR3 удлиняют цикл** — дизайн-стадии начнут спрашивать, стадия 01 требует решения оператора; это задумано, но меняет время прогона.
4. **PR4 (FR/NFR как отдельные типы)** — решение «два типа форм» влияет на реестр и все downstream-стадии (03/05 читают SRS); согласовать до кодинга.
